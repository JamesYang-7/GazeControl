# Running a session and the questionnaire — implementation notes

How a participant session is armed, ordered, labelled, logged and questioned, and the faults that shaped each rule. The operator's procedure is `session-runbook.md`; the questionnaire's UI design is `questionnaire-ui-design.md`. This is the engineering record behind both.

> Moved out of `CLAUDE.md` on 2026-09-11 so that file could stay a high-level guide. This is the design record — decisions, the reasons behind them and the dates they were taken — so keep it current when the behaviour it describes changes.

## Running a session

**One play session runs all fifteen clips.** `StudySessionRunner` (on `GazeCondition`) holds the order, and between clips it re-arms the conversation and the gaze runner **in place** rather than reloading the scene — a reload would tear the headset down and drop the participant out of the experience fifteen times. `GazeConditionRunner.Awake` is factored into `ArmTake()`, which `BeginTake()` also calls, so a later clip goes through the *same* code a fresh play does; a parallel "reset" path is how a re-run comes to differ from a first run.

**The corollary is that scene-derived state must be sampled once, not on every re-arm.** `SmplxMotionPlayer.Initialize` re-read the pelvis rest pose each time a clip was armed, and by then the pelvis was wherever the previous clip's last frame had left it — so each clip inherited the one before it as its origin and the agents walked off their vertices, by a metre or more across fifteen takes (found in a real session, 2026-08-28). The bind pose is now taken once for the life of the component and `Initialize` restores the pelvis to it as it arms, because a clip is armed several frames before its clock starts. `GazeController` had already met the same hazard on the head and guards it by restoring the base rotation before re-sampling. When adding anything read off the scene as a baseline, assume it will be read fifteen times.

**The order between the three is forced and was found the hard way**: `LoadSegment` → `BeginTake` → `PlayLoadedAsync`. The runner validates its baked track against the *loaded* segment's name, so the new segment must be in place before it is armed; but it must be armed before the conversation's clock starts, because that clock is what every decision grid is anchored on. One `RestartAsync` call could not satisfy both, and the track guard caught it by refusing `study_c1`'s track against a still-loaded `study_c5`.

**The clip order is fixed and identical for every participant** (`StudySequence`, pure and unit-tested) — superseding `user-study-design.md` §1's per-participant counterbalancing, so a missing log is identifiable by position. Method order still varies between blocks, balanced so each method sits in each serial position once or twice. See §1 for what that gives up. **The pilot offset is per study** (`StudySessionRunner.PilotCount`, 2026-09-08): study 1 subtracts its four pilots so P05 takes schedule slot 0; study 2 has none and P01 takes slot 0. It was study 1's constant, which would have given study 2's P01-P05 one and the same method order.

**One key does everything.** Space starts the session, skips a running clip to its end, and advances past a pause. At a clip's end the scene holds for the segment's `tailSeconds` (0 means the recorder's 1.5 s default — reading it literally cuts the agents away on the last syllable), then the agents are hidden and both logs close. Hiding them is correctness, not presentation: the runner keeps ticking past the end, so otherwise a participant rates "seemed aware I was there" while two agents gaze at them in a state no condition was baked to produce. **Skip is refused when `StudySession` is on**, because the same key advances and skips and a mistimed press would leave a take that looks complete and is not.

**Logs stop when the take does.** `EndTake()` closes both, idempotently, from the pause controller and from `OnDestroy`. Before it, `RecordFrame` ran unconditionally and the participant sampler sat before the `HasFinished` return, so across twenty pauses most of every file was a frozen skeleton and someone reading a questionnaire. `AutoplayOnStart` and `ArmOnAwake` are both cleared by the session in its `Awake`, so the inspector's leftover clip neither plays before the operator starts nor opens a stray near-empty log in the wrong folder.

**`P00` is reserved for debugging** (`ParticipantLabel.DebugLabel`, the committed default). Real participants start at `P01`. A `StudySession` refuses to start on `P00` or an empty label — every development run writes `P00_…` files, so a participant left on it would file fifteen takes into the debugging namespace. `Next Participant` on the runner's context menu still steps the label by hand, preserving zero-padding; it is a correction path rather than the procedure. **The Alt+N shortcut was removed on 2026-09-01** — a key that silently relabels the next participant's whole session earns its place only while pressing it is the procedure, and it no longer is.

**`GazeControl → Study 2 → Preview Session` plays the bakes with nothing else** (2026-09-08, `StudyPreviewLauncher`): a play-session request like a launch, consumed by `StudySessionRunner.ApplyPreview` — the session's clip order with `Tracks = Replay`, no questionnaire (`QuestionnaireSession.IsRunnable` reads `Session.Preview`), no logs, the developer overlay on with condition and seed, and each clip's end advancing straight into the next through the pause controller, so Space skips the clip that is playing. Nothing it shows is a take. It turns the rig's `StartXrOnPlay` off for the play: with the Varjo runtime up, Windows routes Unity's audio to the headset and the desktop hears nothing (found the same day), so a preview is desktop-only.

**`GazeControl → Help`** is the menu's own index: what each command does, which of them a participant session needs, and the operator keys during play, with an Open button per command and a link to the runbook. It sits at the **foot** of the menu (moved there 2026-09-09, user), separated from the commands it describes.

**A session is started from `GazeControl → Study 2 → Start Session`, not from the inspector** (2026-09-01, `StudySessionWindow`; split into a menu per study on 2026-09-08 — same window, but each opens its own scene first via `StudyScenes.EnsureOpen`, so a session cannot start in the wrong study's scene). **Study 1's menu was taken down on 2026-09-09** (user): its eighteen participants are recorded and its paper written, so the only thing those entries could still do is open the wrong scene by mistake. **`Clip Browser` followed it off the menu on 2026-09-10** (user): it sat at the root as a shared command and is not shared — study 2's clips are chosen from the 3People corpus through `GazeControl → 3People → Session Browser`, which reads a window out as a transcript before anything plays. `StudySessionWindow.OpenForStudy1`, `StudyPreviewLauncher.PreviewStudy1`/`PreviewStudy1InHeadset` and `StudyClipBrowser.Open` are all still there, wanting only their `[MenuItem]` back. Study 2's own menu now leads with `Start Session`, separated from the previews and from the setup and baking commands below them — it is the one command a session needs, and the rest are preparation. **Study 2 also sits at the top of the `GazeControl` menu** and Help at its foot (user, the same day): a submenu takes its place in the parent from its lowest-priority item, so `Start Session`'s priority 0 orders both the row and the submenu, everything else stays at Unity's default 1000, and Help's 2000 clears it by more than the ten a separator needs. It used to take six fields set by hand across three components — the label, `StudySession`, `Tracks`, logging, the session runner's enabled box and the rig's `StartXrOnPlay` — of which two had no guard at all, and the guards that existed fired in `Awake`, i.e. after the participant had the headset on. `Assets/Docs/session-runbook.md` is the operator's procedure.

- **The label is derived, never typed.** `ParticipantRoster` (pure, tested) reads the folders under the study's recordings root (the gaze runner's `OutputDirectory`: `Recordings/Study_01` for TriadScene, `Recordings/Study_02` for Study2Scene — the split made 2026-09-08, with study 1's participants and take logs moved under `Study_01`, demo takes under `Demos` and the `P00_…` debugging runs under `Debug`; `Recordings/README.md` records the layout) and proposes one past the highest — one past the *highest*, not the first gap, because the take logs are named per conversation and survive deleting a folder, so reusing a number is unrecoverable while skipping one costs nothing. It ignores the take folders (`study_c1`, `case1_01`, `cand_v008`) and the timestamped `P00_…` ones. **A label whose folder exists is refused**, which is the hole that had no guard: nothing caught running `P05` twice, and the collision surfaced only when the first questionnaire screen committed — a clip too late.
- **The rules are shared, not duplicated.** `StudySessionRules` (pure, tested) is evaluated over a `StudySessionState` gathered either from the scene at `Awake` (`GazeConditionRunner.StudyState()`, whose guard is now one call) or in Edit Mode by the window. They have to be the same rules, or the window reports ready and `Awake` then refuses. The window additionally answers what only a whole-session view can — all five segments exported, all fifteen tracks baked — which the runner passes as `null` (*not checked here*, deliberately distinguished from *checked and fine*). **A start-key rule refusing an uncalibrated tracker was tried and withdrawn the same day** (2026-09-08/09): `VarjoEyeTracking.IsGazeCalibrating` stayed true on a wearer whose calibration had finished, so the rule held every session forever. P02 and P03 of study 2 ran fifteen clips each on `calibrated=0`, so the operator checks the window's Headset section by eye before starting, and the analysis excludes takes with no usable gaze.
- **The launch touches no scene asset.** Start writes a `StudyLaunchRequest` into `SessionState` and enters play; `StudySessionRunner.Awake` consumes it and applies study mode, `Replay`, logging, its own `enabled`, the rig's headset switch and the developer overlay. They are play-session values, so they vanish on exit and the committed scene keeps its development defaults — there is nothing to put back, and a bake the next morning cannot inherit a half-armed scene. The request is consumed once, so pressing Play again by hand is an ordinary development run.
- **`<recordings root>/<label>/session.json`** (`StudySessionRecord`) is written when the session starts, updated per clip, and stamped `completedUtc` at the end. Nine clips of fifteen otherwise looks exactly like fifteen. It also puts the participant's folder on disk from the first moment, so the roster protects the label even if the session ends before a question is answered, and carries the running order, the schedule ordinal, the Unity version and the commit (`GitHead`, read from `.git` rather than by shelling out — best-effort, null on any failure). The session owns the folder and the questionnaire uses it (`StudySessionRunner.ParticipantDirectory`), so the record and the answers cannot land in two folders. **Since 2026-09-08 the takes live under the participant too**: a study session sets `GazeConditionRunner.TakeRoot` to the participant's folder, so the agent log, sidecar and participant log of each clip are written to `<label>/<clip>/` and deleting `<label>/` removes everything the participant produced. Bakes and demos have no participant and keep writing under `<root>/<clip>/`; a P00 development run with the session runner on files its takes under its timestamped `P00_…` folder beside the answers (2026-09-09; the runner names the folder for every non-preview run, writes `session.json` only for a real session, and the loggers create the folder on the first take). Study 1's eighteen participants stay in the flat layout they were recorded in; `Tools/analyze_participant_gaze.py` searches both.

## The questionnaire

**Two surfaces, one state machine.** `QuestionnaireSession` (on `GazeCondition`) owns the run of 24 screens — 1 framing, 2 previews, 15 rating, 5 ranking-plus-comment, 1 closing — and renders it twice: `QuestionnaireDisplay`, a world-space canvas on the participant's own vertex, and `QuestionnaireOperatorPanel`, an IMGUI panel Unity draws into the desktop window and not into the eye textures. The participant reads the item and either **answers aloud** for the operator to type, or presses the answer on their own button row (below); both go through the one state machine. `GazeControl → Set Up Questionnaire` builds and wires all of it, the row's `QuestionnaireControllerPointer` included.

**Built 2026-08-27, after a VR verification where nothing appeared after a clip.** Only the data layer existed — the instrument, the screen list and the response writer, all pure and tested — and steps 2-4 of `questionnaire-ui-design.md` §9 had never been built, so a session paused with the agents hidden and showed nobody anything. Two decisions from that day also contradicted each other in the repo (the decisions log had the items in VR, `ClipPauseController`'s own doc had them outside it); the user restored the in-VR canvas, and it is what is built.

**The participant may point, but only at their own buttons** (§0.1, user's call 2026-09-09; before that nothing was pointed at at all). A row under the question page — `Undo`, the seven scale points, `Next` on a rating page; `Undo`, `V1`-`V3`, `Next` on the short-answer page — aimed at with a Vive wand and pressed with the trigger, the trackpad click or the grip, *alongside* the spoken path rather than instead of it: a press goes through the same `Enter`/`Back`/`Commit` the operator's keys reach, so `responses.csv` cannot tell which was used and the operator can take over mid-screen. §0's saving is kept — the row is flat rectangles on the same canvas hit by a ray-plane intersection (`PanelRaycast` + `ButtonRowLayout`, pure and unit-tested) and the controller comes straight off the Input System's `XRController` layouts, so there is still no XR Interaction Toolkit, no ray interactor, no event system and no collider. **Every screen but the closing one is pressable** (user, the same day, replacing an answer-screens-only row): a participant who can start a session should be able to finish it, so the framing and the two previews carry a live `Next` too — the previews with their values dim. `Next` on an answer screen lights only once the screen is complete, so nothing can be skipped, and the operator's keys stay live throughout. The closing passage has no row: it is the one screen with nothing after it, and a participant who pressed on would be left in an empty room with the headset on. What is dim is asked of `QuestionnaireEntry.Accepts`, the same predicate that refuses a keystroke. The ranking page now shows the order entered, reversing 2026-08-31 — a press that shows nothing back cannot be checked or corrected. It shows the order as a chain (`Your order:  V2 > V1 > _`); a rank-by-rank spelling (`1st: V2, 2nd: V1, 3rd: _`) was tried the same day and put back, the chain being the shorter line and reading as one order rather than three labelled slots. Which end is best is said in the prompt, which carries "from best to worst". **Working on a real Vive wand pair, 2026-09-09** — both hands aim, both press, the trigger enters an answer — after that first test found two faults: only one wand could highlight, because `TryAim` tested the panel's infinite *plane* rather than the panel, so an idle controller pointing vaguely forward "hit" it metres off to the side and took the cursor from the one actually aimed at a button (the white square at the end of the idle ray is what named it); behind that, the tie-break preferred whichever controller had last *completed a press* — impossible while the trigger was dead — and the device filter took only `XRController`, while the Varjo plugin publishes handed SteamVR *tracker* layouts that do not derive from it, so a wand enumerated that way is lost entirely; and the trigger did nothing (`triggerPressed` was preferred and the axis used only where that control was *absent*, leaving no path for a layout that declares the button and never updates it - both are now read into one down/up state, one edge per pull, with no dependence on `wasPressedThisFrame`). **`TriggerThreshold` is 0.9, on the wand's own click** — the click at the bottom of the travel being the only feedback a participant gets that they pressed anything; release is half of it. It went 0.6 → 0.9 → 0.6 → 0.9 on 2026-09-10: raising it the first time stopped presses registering entirely (the axis does not reach 0.9 here and `triggerPressed` does not fill the gap, though the same wand works in SteamVR's own panel), and it is affordable the second time only because the trackpad click and the grip now press through no threshold — a wand whose ceiling is below the number costs the participant the trigger, not the questionnaire. The operator panel carries each controller's **peak** pull beside the live one, so the ceiling is read off the hardware before the number moves again. **Since 2026-09-10 the threshold cannot lock anyone out**: the wand's **trackpad click** and **grip** press through no threshold at all and are ORed into the same one-edge-per-press state, resolved and read exactly as the trigger is (descriptor first, both input surfaces, `primary2DAxisClick` / `gripButton` / `grip`), with the touch sensors excluded by requiring "click" or "press" in the name and the System button unavailable because SteamVR reserves it. The peak stays the trigger's alone, or a pad click would read 1.00 for ever and answer "is this threshold reachable?" wrongly for the rest of the session; the operator's per-controller line gained a `pad/grip:` field, and the framing screen now tells the participant to click the trackpad with the trigger as the alternative. **A fresh clone on a second PC then answered nothing until `Log XR input snapshot` had been pressed once** — a persistent fix, because the XR subsystem belongs to the editor process and not the play session — and the button was doing what the normal path skipped: `XRInputDevices.GetDevices` lived in exactly two places, the snapshot unguarded and `LegacyControls.Resolve` behind an early-out on having neither serial nor name, both captured in `Rescan` before the rig starts XR. Fixed with two more of the same shape: the match now falls back to the hand alone (SteamVR assigns hand roles *after* the wands come up, so the captured characteristics go stale), and the feature flags are re-scanned instead of latching false on the one frame the device was matched — a latch that made a working controller declare itself dead while its values read fine. `Rescan` wakes the legacy surface unconditionally and logs both surfaces' controller counts. **A pull of 0.00 for a whole screen** (2026-09-10, study 2's scene, the same wand working SteamVR's own dashboard) had two possible readings on the Input System side and both are now closed. The trigger is looked up through the device's **XR descriptor** rather than its layout's control names: `XRLayoutBuilder` assembles an XR device's controls out of the features the runtime reports, so a control the vendor's layout declares and no feature backs is still found by name and reads zero for ever - which made `TryGetChildControl("trigger")` succeed on every wand and prove nothing, and left the fallback that searches for a trigger-shaped control unreachable (`XrFeatureControlName`, pure and unit-tested, is the builder's own naming rule). And it is read through the legacy `UnityEngine.XR.InputDevices` subsystem as well, matched to the same hardware by serial number, which asks the runtime for the trigger by usage and cannot be caught out that way; the pull is whichever surface reports more and the operator's line names both (`trigger 0.83 (IS 0.00 · XR 0.83, ...)`). Neither is confirmed on hardware. **`Log XR input snapshot`**, a button on the operator panel and a context menu item on the pointer, writes every tracked device's descriptor features and every legacy usage's live value in one entry - which is what separates a trigger control that is missing, one that is present and unmapped, and a runtime giving this application no button input at all. The **scene** decides it, not the C# default (the field is serialized, and both scenes sat on 0.6 after the default moved): `GazeControl → Set Up Questionnaire` owns the number as a constant and writes it into the scene on every run, logging the correction, and the pointer logs the value it is actually using as the controllers are found — so a stale scene shows in the first seconds rather than never. The operator panel carries **a line per controller** — hand, tracked or not, where on the panel it points, how far its trigger is pulled — because every fault so far has looked identical from the desk ("the controller does nothing"); `LogControlsAsPressed` adds what is held by control name, for an unfamiliar controller. `MouseFallback` (off by default, because the operator's clicks land in the same game view) is how the row is walked at a desk. A rating screen is headed by the instrument's `ratingTitle` and lists the four items numbered, each behind a box — `>` marks the one being asked and the number the operator types appears in that item's box, so a participant can watch a spoken answer land and say so when it was heard wrong (2026-09-02, replacing the marker-only list that deliberately showed nothing back). **The ranking and the free-text probe share one page**, headed by `shortAnswerTitle` and numbered on from the rating items (5 and 6, derived from `perClipItems.Length`) (2026-09-02). It shows the two prompts, a `>` against the one being asked (2026-09-09, the rating page's own convention: two questions on a page whose button row changes under them, so which the row is answering has to be visible) and, once anything is entered, the order given; D1 carries its own "(optional)" in the prompt and has no instruction line on either surface, while the ranking's "no ties" stays operator-side — under a foot naming the group about to be watched (`nextGroupFormat`, "Next: group 3"), which is the participant's only sense of where they are in a session of five and says nothing after the last group. **Both question pages are shown once before the first clip**, as the rating preview then the short-answer preview (`QuestionnaireScreenKind.RatingPreview`/`ShortAnswerPreview`, the matching `Phase`s), each answering nothing and passed with one press of the operator's key: a participant who knows they will rate four things and then rank the three versions watches the first group for what they will be asked about. The rating preview is the rating page itself with no entry behind it, so every box is blank and nothing carries the `>`. The operator still enters them as two screens, because they are two records and the ranking refuses a tie. **The ranking listed no versions at all** from 2026-08-31 — the prompt and nothing else, because the participant named the three in order aloud and listing them only invited them to do the ranks-to-versions conversion themselves; since 2026-09-09 it shows the order they have entered, for the reason above. The rating screen's scale line is led by `scale.rangeHint`, composed with the scale's own bounds: the three anchors alone read as a three-option menu and participants asked whether they were choosing from 1, 4 and 7. **Nothing tells the participant to answer aloud any more** — `spokenAnswerInstruction` was on the foot of every page and is deleted from the instrument (2026-09-02); the operator says it.

**The operator panel is blinded** (§2). It shows `Conversation 3 · Version 2 of 3` and never the method behind a version. The experimenter reads the items aloud and knows the hypothesis, so naming the condition would tell them which answer is the interesting one; the condition reaches `responses.csv` straight from `StudySequence` and is displayed nowhere. Keys: `1-7` answers each item in turn, `Backspace` undoes, `Enter` commits the screen and releases the next clip; the ranking takes `1-3` with **ties refused**; the comment is a text field committed with `Ctrl+Enter`. Every key is read from `Event.current` inside `OnGUI` rather than through the Input System, so typing a comment cannot also enter a rating.

**A screen holds the session.** `ClipPauseController.AdvanceHeld` and `StudySessionRunner.StartHeld` are set while a screen is unanswered, and the pause controller yields the whole key — the skip included — so one operator key cannot walk past an unanswered screen. With no questionnaire in the scene both stay false and the pause works exactly as before. `GazeConditionRunner.StudySessionProblem()` refuses a study session with no `QuestionnaireSession` in the scene, because fifteen clips that ask nothing is a session that looks complete and measures nothing.

**Answers are written as they are entered**, into `<recordings root>/<participant>/`: `responses.csv` (`participant, block, conversation, version_position, condition, item, response, utc`) and `comments.jsonl` for the free text, which is kept out of the numeric file because it contains commas and newlines by nature. A screen is committed as a whole rather than per keystroke, so a mistyped answer can still be corrected — `QuestionnaireResponseWriter` takes each question exactly once and offers no amendment. A real participant's folder is opened once and never reopened; **`P00` takes a timestamped folder instead**, or the second development run of the day would refuse to start for a reason that has nothing to do with the study.

The entry rules are `QuestionnaireEntry` (pure, 17 tests): slots, a cursor, the scale bounds, and whether repeats are allowed. A clip that was **cut short** (`ClipPauseController.WasCutShort`) puts its screen up with recording disabled — a rating of half a clip is worse than a missing one, because nothing downstream can tell them apart.

It runs **only when `StudySessionRunner` is enabled**: a bake, a demo recording and a preview all press Play in this same scene, and turning that runner off is already how each of them says it is not a participant run.

Still to check on hardware: that the IMGUI panel really is invisible in the Varjo (§1 — the assumption the two-surface split rests on), legibility at 1.5 m, and whether a Vive wand enumerates under the Varjo loader and its 11 cm buttons are comfortable to hit at 1.5 m (§0.1). Panel geometry lives on `QuestionnaireDisplay` (`EyeHeight`, `Distance`, `PanelSize`, `BodyFontSize`), which places itself in `Awake` rather than trusting the scene transform — a `RectTransform`'s position is expressed through anchors and an offset written by a setup script does not reliably survive.
