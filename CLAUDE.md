# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

A gaze control demo for virtual agents in a triad conversation: two virtual agents (A and B) plus the user. Gaze behavior patterns collected from real triad conversations (gaze shifts preceding turn-taking) drive the agents' gaze control. Motion control of the agents is also data-driven.

Target demo scenes:
1. **Agent-to-agent turn-taking** — turn-taking happens between agent A and agent B while the user just watches.
2. **Turn-yielding to the user** — agent A wants the user to take the turn and signals this with gaze.

## Environment

- **Unity 6000.5.3f1** (Unity 6) with the **Universal Render Pipeline (URP)**.
- Input handled via the **Input System** package (`Assets/InputSystem_Actions.inputactions`).
- **Timeline** and **Unity Test Framework** packages are installed.
- The project is currently a fresh URP template: `Assets/Scenes/SampleScene.unity`, URP settings under `Assets/Settings/`, and removable template files under `Assets/TutorialInfo/`.

## SMPL-X

The agents use the SMPL-X body model. Two code layers drive it:
- `Assets/GazeControl/Scripts/Runtime/Motion/` (ours) — .npz clip loading and playback (`SmplxMotionPlayer` writes joint local rotations in `Update`).
- `Assets/SMPLX/Scripts/SMPLX.cs` (official MPI package, imported verbatim — do not restyle) — pose correctives (486 blendshapes recomputed in `LateUpdate` from current joint rotations, composing cleanly with our player), betas/expressions, hand/body pose presets. Depends on `Assets/SMPLX/ThirdParty/` and the regressor JSONs in `Assets/SMPLX/Resources/`.

License: SMPL-X model license (research use; cite the SMPL-X paper in publications). The Meshcapade sample textures are CC BY-NC.

## Speech and the recorded conversation

**The agents speak the corpus's own audio, not synthesised speech.** `RecordedConversation` replays a 20-30 s segment of a real TalkingWithHands dyadic conversation: each agent gets that recording's wav on its `AudioSource` and its 60 fps grounded SMPL-X motion, and the corpus's annotated end-of-turn events become the turn schedule the gaze policies read. Corpus speaker 1 (`main-agent`) is agent A, speaker 2 (`interloctr`) is agent B; the human user is the silent listener.

Everything runs on one clock, `RecordedConversation.Elapsed` — the frame clock, because Unity Recorder writes one output frame per rendered frame, so a take's timeline *is* the frame count. Both voices are scheduled on a single DSP instant so the two sides cannot start a frame apart. An audio-clock version of `Elapsed` was tried and produced a take 0.7 s shorter than the segment with the last utterance clipped; see the property's comment.

The Kokoro-82M TTS integration (`Assets/TTS/`, `KokoroTts`, `TtsSpeaker`) and the scripted `TriadConversation` were **deleted on 2026-08-10** when this replaced them. They are in the git history.

## Demo segments

The corpus is at `F:\Data\TalkingWithHandsCentered` (see its own README): `talkingwithHands-Audio/{main-agent,interloctr}/{wav,tsv}`, `SMPLX-60fps-grounded/` (the motion variant we use), and `EoT_TWH/` — 186 deduped conversations, 6,953 end-of-turn events typed 1 interruption / 2 overlapping / 3 turn-taking, times in ms.

`Tools/find_demo_segments.py` picks the stretch that gets played and exports it to `Assets/DemoSegments/<name>/` (git-ignored): two trimmed wavs plus `segment.json` (schema `gazecontrol.demo-segment/2`) with the turn schedule, the events and the motion frame offset. Motion is read from the corpus in place. Scene-1 selection requires 20-30 s, ≥2 events fully inside with lead, boundaries on utterance boundaries with nothing straddling them, and ≥2 s between consecutive turn instants; candidates are then ranked for demo readability. `--inspect <rank>` prints a segment as a transcript with its events marked.

**`--scene2` searches for turn-yields to the user instead**: a 20-30 s window that *ends* at a turn-taking event closing a monologue (no other annotated event inside by default; the other speaker limited to backchannels; the yielder talking ≥10 s), ranked with question-final closers in a hard first tier (the transcripts are punctuated — `?` is a direct test). The exported schedule names the user (**speaker code 0**) as the final turn's taker with the yield event's real index — no `-1` final turn — plus `yieldsToUser` and a `tailSeconds` hold the recorder reads (`DemoRecorder` holds that long after the voices stop; 0 = its 1.5 s default). A scene-2 export runs a self-check on the written JSON and fails loudly on any contract violation. `RecordedConversation.User` must be wired to the human participant for a yield segment to load, and `ProposedGazePolicy` plays the prototype's **listener track** for a participant in neither boundary role (in scene 2 that is the other agent; unreachable in scene-1 schedules). `--allow-internal-events` admits interruptions/overlaps (never internal turn-takings — whether a bystander could join after real turn-taking is a semantic judgment made by reading `--inspect`, not by rule).

Voices are **measured, not annotated** — see Agent appearance. `--voice male` walks the ranking and measures pitch lazily, so a filtered search only reads the audio it needs.

**The exporter peak-normalises the pair** (to 0.70, one gain for both sides from the louder track). The corpus records around **−42 dBFS**: at raw levels no frame reaches `VoiceRmsThreshold` (0.01), so baseline B never detects anyone speaking and both agents stare at the human user for the whole take. The gain is shared because the balance between the two speakers is recorded rather than incidental; it is written into `segment.json`. The base `wav/` tracks *are* properly speaker-separated (8-16× energy ratio during their own speaker's words) — only the level was wrong.

## Lip sync

Oculus LipSync (`Assets/Oculus/LipSync/`, third-party, verbatim) drives the mesh's 14 viseme blendshapes (indices 506–519, Oculus order minus `sil`) from each agent's `AudioSource`. Per agent: `AudioSource` + `OVRLipSyncContext` (`audioLoopback` **on**, or the voice is muted) + `OVRLipSyncContextMorphTarget` (`laughterBlendTarget` must be **−1**; the default 15 would drive an expression blendshape). The scene needs one `LipSync` GameObject with the `OVRLipSync` component. Nothing extra is wired for the demo segment: the context analyses whatever its `AudioSource` plays, which is the corpus wav.

The mesh carries a **mouth bag** (added in Blender) so the open mouth is no longer a hole. The bag is unmapped — all 161 of its vertices sit on UV (0, 0) — so it would otherwise take the colour of the albedo's bottom-left texel, which differs per agent texture. `SmplxMouthInteriorSubmesh` (an `AssetPostprocessor`, editor-only) therefore moves every triangle whose three vertices are all on UV (0, 0) onto submesh 1 at import and assigns `Assets/SMPLX/Materials/SMPLX-MouthInterior.mat`. Adjust that material to change how dark the cavity reads; no reimport needed. `GazeControl → Visemes → Open Jaw` drives the `aa` viseme in Edit Mode so you can see inside.

Caveat: with the Unity editor unfocused, the player loop and edit-mode skinning stall (`Time.time` freezes in Play Mode; `Camera.Render()` captures show stale meshes). Set `Application.runInBackground = true` **each Play Mode session** when driving the editor unfocused (the `PlayerSettings` flag does not govern editor play, and the runtime flag resets on exit). Skinning/blendshape changes made in the same editor command they're rendered in won't show — render in a later command.

## Gaze control

Gaze patterns come from the ICMI paper in `Assets/Docs/` (Figures 6–8: top gaze subsequences in the 1 s before turn events, 60 Hz, encoded over conversational roles — red = current speaker, blue = next speaker, green = listener; y-axis = gaze target). **All fifteen printed prototypes** are transcribed from the raw prototype archives (`raw_prototypes/*.npz` under `{ICMI_ROOT}` = `F:\Research\ICMI_2026___Explainable_Gaze_Patterns_for_Turn_Taking`, moved there from `F:\aF\My_Papers\` on 2026-09-08) by `Tools/build_gaze_patterns.py` into the generated `GazePatterns.g.cs` — never edit that file by hand. They are named by figure (`Fig6a`…`Fig8e`) and pooled by class: 5 interruption, 4 overlapping, 6 turn-taking. The generator asserts that Fig7e and Fig8d still decode to the two transcriptions the earlier demos were signed off on.

The **full gaze corpus** behind those prototypes — the complete per-frame sequences, not just the pre-turn second — is `Research/corpora/gaze_events/gaze_events_md6.csv`: 120,765 role-coded fixations over 38 sessions at 60 fps that tile each participant's timeline losslessly (its own README documents the schema and caveats; read §6 before trusting the `ad` role). `Tools/build_baseline_a_params.py` fits baseline A from it. Upstream sources, outside the repo: per-frame gaze targets in `F:\Data\GazePattern\Gaze_mocap_{2022,2024}_r40\<session>_gaze_target.csv` and EoT annotations in `F:\Data\GazePattern\EoT_{2022,2024}\<session>_eot.csv`, rebuilt into the CSV by the `gazeturn` package at `F:\Code\scnpro\prototype\prototype` (`python -m gazeturn.labeling.gaze_events`). Note `Research/corpora` is a plain local copy, not a junction — unversioned and not a backup.

**All gaze runs through `IGazePolicy`.** `GazeConditionRunner` builds one policy per agent, ticks it at a fixed 60 Hz decision rate decoupled from the frame rate, and applies the result; `RecordedConversation` drives only playback and the turn schedule and never touches a gaze target. The three experimental conditions are the `Condition` dropdown on the `GazeCondition` object:

- `SpeakerFollowing` — baseline B, voice-activity driven, never averts. §3's rules apply symmetrically to the agent itself: it will not switch on its *own* sub-600 ms utterance (a backchannel is a backchannel whoever produces it), and it never takes itself as addressee. `ConversationState.CurrentAddressee` belongs to whoever holds the floor, so with real audio it names *this* agent whenever it talks over someone — which is what a backchannel is. In that case the agent it is addressing is the **floor-holder it is answering** (`CurrentSpeaker`); the human fallback applies only when neither field names anyone else. Falling back to the human directly was tried and left an agent staring at the user for 66% of a take.
- `RoleConditioned` — baseline A, the Shintani et al. 2024 model re-fitted to our corpus (`Assets/GazeControl/Resources/BaselineAParameters.json`, regenerated by `Tools/build_baseline_a_params.py`).
- `Proposed` — a prototype played over a **holding-replay substrate**, overriding it only in the window before each annotated end-of-turn event. Outside the windows the agent replays measured holding-period fixation stretches from the full gaze corpus, conditioned on its current role (`HoldingReplayGazePolicy` + the committed `Assets/GazeControl/Resources/HoldingSequences.json`, regenerated by `Tools/build_holding_sequences.py`); replay aversion renders as recentred eyes, exactly like the prototypes' `None`, and the stretch draws are **per-agent** seeded streams — holding gaze is uncoordinated in the corpus. `ProposedSettings.Substrate = SpeakerFollowing` is the prototype-only ablation: bit-for-bit baseline B outside the windows, isolating the pattern exactly (the pre-2026-08-14 arrangement). Each event draws its own prototype from the pool matching **its own class**, so an interruption is preceded by an interruption prototype. That draw is `FNV-1a(BaseSeed, eventIndex)`, deliberately *not* per-agent — both agents must play tracks of the same prototype — and the whole mapping is written into the log's metadata sidecar before the first boundary. `ProposedSettings.Selection = Fixed` pins one prototype instead; `PatternTimeScale` 1 is data-faithful.

`ConversationDirector` publishes the segment's turn schedule (who holds the floor, who takes it next, when the boundary is, and which event it is) so a policy can act *before* a boundary rather than react after it; baselines A and Proposed require it. **It is driven, not self-advancing**: `GazeConditionRunner` calls `SyncTo(k · step)` once per decision tick, so every time the director publishes — time to the boundary, time since the last one, turn phase — is measured on the decision grid rather than at the sub-frame instant the frame clock happened to read. It used to pull a clock delegate on every read (to dodge the `Update` ordering between it and the runner); that made two bakes of one seed disagree on single-frame prototype segments, and being driven removes the ordering hazard outright. The segment's final turn carries `eventIndex = -1` and no prototype fires there.

`GazeController` is the shared animation layer — identical in every condition, or the study measures animation instead of gaze policy. It drives the SMPL-X eye bones only: `HeadContribution` is **0**, so the head stays on pure mocap. Yaw and pitch are clamped separately (±35° / ±25°). Aversion is a direction (`SetAversion(yaw, pitch)`, eye-in-head); a zero offset means "eyes recentred in the head", which is how the proposed condition renders the prototypes' `None`. No blink model (SMPL-X has no eyelid shapes) and no idle micro-motion — body motion comes from the mocap clips.

`ListenerCamera` remains in the codebase but is wired to nothing since gaze moved behind the policy interface.

## XR — the study rig

The study runs live in a **Varjo** headset on **tethered PC VR**. The backend is the **Varjo Unity XR plugin** (`com.varjo.xr`), which is the active Standalone loader; `com.unity.xr.openxr` stays installed but inactive. Settings live in `Assets/XR/` and must be committed.

**It was OpenXR first, and the switch is deliberate** (2026-08-27). The port was built and verified against OpenXR, and on real hardware that path works: the runtime reports itself as `Varjo OpenXR Runtime 4.14.0`, renders stereo, gives a Floor origin and holds 90 fps with both agents. What it would not give is gaze — `XR_EXT_eye_gaze_interaction` was both available *and* enabled on the instance, yet no gaze device ever appeared (`GetDevicesWithCharacteristics(EyeTracking)` returned 0, nothing exposed `eyesData`). Varjo's own plugin is the answer to that, and it gives more than the extension does: per-eye rays, pupil size and focus distance rather than one combined ray. **The eye-gaze measures of §7 are built on `VarjoEyeTracking`, not on OpenXR input.** The OpenXR feature set (Eye Gaze Interaction plus the Index / Vive / KHR controller profiles) is still configured, so switching the loader back is a one-line change if the vendor path ever disappoints.

**The headset never carries the audio.** This Varjo has no speakers, but starting XR still makes the runtime point Unity's audio engine at the headset's virtual device, and the switch back on stop failed ("FMOD failed to switch back to normal output") and left the editor silent with every source reporting playing (2026-09-08). `XrParticipantRig` therefore re-initialises the audio engine on Windows' default output right after XR starts and again after it stops (`KeepSystemAudioOutput`, on by default); a reset stops whatever is playing, which is why it happens at the switch and never during a clip. `GazeControl → Reset Audio` is the same reset by hand.

**XR does not start by itself, on purpose.** "Initialize XR on Startup" is unchecked, and `XrParticipantRig.StartXrOnPlay` (off in the committed scene) is the only switch. Baking gaze tracks, browsing clips and recording demo videos all press Play on a machine that may have no headset, and auto-initialisation would break every one of them.

The rig is `User` (the triad vertex, unmoved) → `Camera Offset` (carries the eye-height offset) → `Main Camera` (`TrackedPoseDriver` on the centre eye). Flat, and in a headset at the moment of recentring, the camera sits at the same **1.6846 m**, so a desktop preview and a worn take start by framing the triad identically. `GazeControl → Set Up XR Rig` builds or repairs the rig; nothing else in the scene changed, because the agents already aim at the user's `LookAtAnchor` and that is this camera — in a headset they aim at the participant's real head.

**The participant's head is placed once and then tracks freely, position and rotation both** (user's call, 2026-09-08, replacing the fixed viewpoint of 2026-08-27). `TrackedPoseDriver.trackingType` is `RotationAndPosition`; recentring (`XrParticipantRig.RecentreView()`) moves *and* turns the play area (`Camera Offset`) so that the headset's current pose lands on the triad vertex at **1.6846 m** facing between the two agents, and from then on the camera follows the head wherever it goes. Every participant therefore *starts* from the identical point on the agents' shared eye line, and only their own movement from there differs. The participant's own height is deliberately not kept — a short participant starts on the eye line, not below it — and it is still read off the device each frame into `MeasuredEyeHeight` as a covariate.

That height is the SMPL-X agents' own eye line, measured off their `left/right_eye_smplhf` bones — the participant is the third head on the shared eye line rather than 8.5 cm below it, which is where the previous generic 1.60 m sat them. Under mocap the agents' eyes travel **1.663-1.713 m** with a mean **3 mm** below the rest-pose value, so the starting height is level with them to within their own sway. `ParticipantEyeHeight.SmplxEyeHeight`, and a serialized field on the rig if it ever needs retuning.

**The fixed viewpoint it replaces** (2026-08-27 to 2026-09-08, `RotationOnly`) bought identical geometry for every participant and a deterministic rendered gaze from the agents, at the cost of no positional parallax: leaning moved nothing and turning the head pivoted the world about the eyes rather than the neck. The user chose parallax. The agents aim at the human's `LookAtAnchor`, which is this camera, so their rendered gaze now follows the participant's real head and differs between participants by however far they moved; the participant log's head pose columns record it. No baked gaze track is affected: a policy names a target, never an angle, and the only policy input derived from scene geometry, `ConversationState.MutualGazeActive`, has been unread since mutual-gaze breaking was dropped on 2026-07-30.

**Recentring, because the room's tracking origin is arbitrary.** The headset's origin and yaw zero come from the room's tracking setup, not from where the participant is standing, so a session can otherwise start with the triad off to one side, behind them or a metre away. It fires automatically on the first frame after XR start that reports a usable pose (`RecentreOnXrStart`, on by default, giving up after 15 s so a headset picked up mid-take cannot snap the view), and the operator repeats it from the component's context menu with the participant **on the mark, looking straight ahead**.

**Yaw only** (`ViewRecentring`, pure and unit-tested): pitch and roll are reported against gravity and are already correct, so turning them would tilt the virtual horizon away from the real one. The yaw is taken from the forward vector's horizontal projection rather than from `eulerAngles.y`, which mixes roll into yaw near the poles, and a head pitched more than ~80° from level is **refused rather than guessed** — yaw is undefined looking straight up. The position offset is the vertex at eye height minus the head position turned by that yaw. It reads the **raw device pose**, not the camera, so recentring twice re-measures instead of compounding. "Centred between the agents" is exactly "yaw zero relative to the rig root": the User vertex faces the triad centroid, which for the equilateral layout is the agents' midpoint — measured **0.32°** off, which is the agents' own head asymmetry. `GazeControl → Set Up XR Rig` warns if that ever drifts past 3°.

**A participant who walks now sees it**, so the operator asks them to stay on the mark and recentres between clips if they have drifted. Comfort in the headset and whether the geometry reads eye-to-eye are still pilot questions.

`ParticipantEyeHeight` (pure, unit-tested) is what is left of the old per-participant calibration: the constant plus the 1.20-2.10 m plausibility bounds. `XrParticipantRig` reads the headset device's own height each frame into `MeasuredEyeHeight` — off the device, not the camera, since the camera's height is the device's plus the recentring shift — purely so the participant's real height is on record as a possible covariate. A sample outside the bounds keeps the last real one rather than overwriting it.

**Verified on a real Varjo, 2026-08-27, through the OpenXR path**: subsystems start, tracking origin is Floor, stereo renders, the head pose drives the camera, and the scene holds **90 fps** with two SMPL-X agents, 486 correctives and LipSync — the frame-rate risk is closed. Before that it was checked under the **OpenXR Mock Runtime** (disabled in the committed settings; re-enable temporarily to repeat), which also showed calibration moving a simulated 1.85 m participant's eyes to exactly 1.600 m.

**Participant gaze is logged, in its own file on the decision grid.** `ParticipantGazeLogger` (on the `User` vertex, driven by `GazeConditionRunner.Tick`, built and wired by `GazeControl → Set Up XR Rig`) writes `<stem>_user.csv` into the take's folder beside the twenty-column agent log, one row per decision tick: tracker and per-eye status, the combined and per-eye rays in **world space**, head pose, focus distance, pupil diameters and eye openness, plus what the ray resolved to. Two files rather than more columns on one, because the agent log records what was *rendered*, once per frame, and this records what was *decided against*, once per tick — merging them would take one of the two off its own clock.

Gaze comes through `IParticipantGazeSource`; `VarjoGazeSource` is the only implementation and it drains `VarjoEyeTracking.GetGazeList` (one native fetch returning aligned gaze/measurement pairs — `GetGaze` + `GetEyeMeasurements` are two fetches and can straddle a tracker frame). The tracker runs at 100–200 Hz against the 60 Hz grid, so a tick with no new frame repeats the last sample and the logged `device_frame` is what says so.

**Which agent is being looked at is a head *sphere*, not a cone** (`GazeSphereTargeting`, pure and unit-tested): an angle is a different amount of head at every distance and the participant can step. That makes the two halves of mutual gaze use different criteria — the participant→agent half a 0.15 m sphere, the agent→participant half the runner's 15° cone — so `target_angle_deg` is logged and the sidecar records both thresholds, leaving the threshold an analysis choice rather than a baked-in one. `agents_looking_at_user` is a bit set over agent ids, so gaze-return latency (§7.4) needs no join against the agent log. **It is sampled at end of frame, not on the tick** (fixed 2026-09-08): the tick runs in `Update` after the motion player has written the clip's zero rotation into the eye joints and before `GazeController.LateUpdate` re-aims them, so read there the "rendered" direction was the mocap head's and the column came out identical across conditions. Both files' `t` is the conversation clock (the agent log's was the session clock until the same day, which put every take after a session's first at an unrecorded offset). `Tools/analyze_participant_gaze.py` reports a session's takes and `--check` compares the two files. **Nothing is written on a desktop Play** (baking, clip browsing and Record Demo all run headless), and a `StudySession` now also refuses to start with no participant gaze logger wired.

**Still unverified, and the first thing to do next**: nothing has been run through the *Varjo loader* yet — the measurements above are the OpenXR path, and the loader switch came after them. Also open: the recentred, freely tracking viewpoint has never been worn (comfort and whether the geometry reads eye-to-eye are both pilot questions), **no gaze has yet been read from real hardware** (the pipeline above is built and tested but has only ever seen "no headset"), §7's four derived measures are not computed anywhere, there is no in-VR questionnaire, and per-participant calibration is not persisted. Note for whoever debugs gaze: Varjo gates eye tracking behind a permission in **Varjo Base** and behind its own per-wearer ET calibration (`XrParticipantRig.CalibrateEyeTracking()` requests it), and some runtimes suppress gaze entirely while the headset is off the head — `VarjoGazeSource.UnavailableReason` names whichever of the three failed.

## Running a session

**One play session runs all fifteen clips.** `StudySessionRunner` (on `GazeCondition`) holds the order, and between clips it re-arms the conversation and the gaze runner **in place** rather than reloading the scene — a reload would tear the headset down and drop the participant out of the experience fifteen times. `GazeConditionRunner.Awake` is factored into `ArmTake()`, which `BeginTake()` also calls, so a later clip goes through the *same* code a fresh play does; a parallel "reset" path is how a re-run comes to differ from a first run.

**The corollary is that scene-derived state must be sampled once, not on every re-arm.** `SmplxMotionPlayer.Initialize` re-read the pelvis rest pose each time a clip was armed, and by then the pelvis was wherever the previous clip's last frame had left it — so each clip inherited the one before it as its origin and the agents walked off their vertices, by a metre or more across fifteen takes (found in a real session, 2026-08-28). The bind pose is now taken once for the life of the component and `Initialize` restores the pelvis to it as it arms, because a clip is armed several frames before its clock starts. `GazeController` had already met the same hazard on the head and guards it by restoring the base rotation before re-sampling. When adding anything read off the scene as a baseline, assume it will be read fifteen times.

**The order between the three is forced and was found the hard way**: `LoadSegment` → `BeginTake` → `PlayLoadedAsync`. The runner validates its baked track against the *loaded* segment's name, so the new segment must be in place before it is armed; but it must be armed before the conversation's clock starts, because that clock is what every decision grid is anchored on. One `RestartAsync` call could not satisfy both, and the track guard caught it by refusing `study_c1`'s track against a still-loaded `study_c5`.

**The clip order is fixed and identical for every participant** (`StudySequence`, pure and unit-tested) — superseding `user-study-design.md` §1's per-participant counterbalancing, so a missing log is identifiable by position. Method order still varies between blocks, balanced so each method sits in each serial position once or twice. See §1 for what that gives up.

**One key does everything.** Space starts the session, skips a running clip to its end, and advances past a pause. At a clip's end the scene holds for the segment's `tailSeconds` (0 means the recorder's 1.5 s default — reading it literally cuts the agents away on the last syllable), then the agents are hidden and both logs close. Hiding them is correctness, not presentation: the runner keeps ticking past the end, so otherwise a participant rates "seemed aware I was there" while two agents gaze at them in a state no condition was baked to produce. **Skip is refused when `StudySession` is on**, because the same key advances and skips and a mistimed press would leave a take that looks complete and is not.

**Logs stop when the take does.** `EndTake()` closes both, idempotently, from the pause controller and from `OnDestroy`. Before it, `RecordFrame` ran unconditionally and the participant sampler sat before the `HasFinished` return, so across twenty pauses most of every file was a frozen skeleton and someone reading a questionnaire. `AutoplayOnStart` and `ArmOnAwake` are both cleared by the session in its `Awake`, so the inspector's leftover clip neither plays before the operator starts nor opens a stray near-empty log in the wrong folder.

**`P00` is reserved for debugging** (`ParticipantLabel.DebugLabel`, the committed default). Real participants start at `P01`. A `StudySession` refuses to start on `P00` or an empty label — every development run writes `P00_…` files, so a participant left on it would file fifteen takes into the debugging namespace. `Next Participant` on the runner's context menu still steps the label by hand, preserving zero-padding; it is a correction path rather than the procedure. **The Alt+N shortcut was removed on 2026-09-01** — a key that silently relabels the next participant's whole session earns its place only while pressing it is the procedure, and it no longer is.

**`GazeControl → Study 1 / Study 2 → Preview Session` plays the bakes with nothing else** (2026-09-08, `StudyPreviewLauncher`): a play-session request like a launch, consumed by `StudySessionRunner.ApplyPreview` — the session's clip order with `Tracks = Replay`, no questionnaire (`QuestionnaireSession.IsRunnable` reads `Session.Preview`), no logs, the developer overlay on with condition and seed, and each clip's end advancing straight into the next through the pause controller, so Space skips the clip that is playing. Nothing it shows is a take. It turns the rig's `StartXrOnPlay` off for the play: with the Varjo runtime up, Windows routes Unity's audio to the headset and the desktop hears nothing (found the same day), so a preview is desktop-only.

**`GazeControl → Help`** is the menu's own index: what each of the thirteen commands does, which of them a participant session needs, and the operator keys during play, with an Open button per command and a link to the runbook. It sits at the top of the menu, separated from the commands.

**A session is started from `GazeControl → Study 1 → Start Session` or `Study 2 → Start Session`, not from the inspector** (2026-09-01, `StudySessionWindow`; split into two menus on 2026-09-08 — same window, but each opens its own scene first via `StudyScenes.EnsureOpen`, so a session cannot start in the wrong study's scene; `Clip Browser` is shared and sits at the menu root). It used to take six fields set by hand across three components — the label, `StudySession`, `Tracks`, logging, the session runner's enabled box and the rig's `StartXrOnPlay` — of which two had no guard at all, and the guards that existed fired in `Awake`, i.e. after the participant had the headset on. `Assets/Docs/session-runbook.md` is the operator's procedure.

- **The label is derived, never typed.** `ParticipantRoster` (pure, tested) reads the folders under the study's recordings root (the gaze runner's `OutputDirectory`: `Recordings/Study_01` for TriadScene, `Recordings/Study_02` for Study2Scene — the split made 2026-09-08, with study 1's participants and take logs moved under `Study_01`, demo takes under `Demos` and the `P00_…` debugging runs under `Debug`; `Recordings/README.md` records the layout) and proposes one past the highest — one past the *highest*, not the first gap, because the take logs are named per conversation and survive deleting a folder, so reusing a number is unrecoverable while skipping one costs nothing. It ignores the take folders (`study_c1`, `case1_01`, `cand_v008`) and the timestamped `P00_…` ones. **A label whose folder exists is refused**, which is the hole that had no guard: nothing caught running `P05` twice, and the collision surfaced only when the first questionnaire screen committed — a clip too late.
- **The rules are shared, not duplicated.** `StudySessionRules` (pure, tested) is evaluated over a `StudySessionState` gathered either from the scene at `Awake` (`GazeConditionRunner.StudyState()`, whose guard is now one call) or in Edit Mode by the window. They have to be the same rules, or the window reports ready and `Awake` then refuses. The window additionally answers what only a whole-session view can — all five segments exported, all fifteen tracks baked — which the runner passes as `null` (*not checked here*, deliberately distinguished from *checked and fine*).
- **The launch touches no scene asset.** Start writes a `StudyLaunchRequest` into `SessionState` and enters play; `StudySessionRunner.Awake` consumes it and applies study mode, `Replay`, logging, its own `enabled`, the rig's headset switch and the developer overlay. They are play-session values, so they vanish on exit and the committed scene keeps its development defaults — there is nothing to put back, and a bake the next morning cannot inherit a half-armed scene. The request is consumed once, so pressing Play again by hand is an ordinary development run.
- **`<recordings root>/<label>/session.json`** (`StudySessionRecord`) is written when the session starts, updated per clip, and stamped `completedUtc` at the end. Nine clips of fifteen otherwise looks exactly like fifteen. It also puts the participant's folder on disk from the first moment, so the roster protects the label even if the session ends before a question is answered, and carries the running order, the schedule ordinal, the Unity version and the commit (`GitHead`, read from `.git` rather than by shelling out — best-effort, null on any failure). The session owns the folder and the questionnaire uses it (`StudySessionRunner.ParticipantDirectory`), so the record and the answers cannot land in two folders.

## The questionnaire

**Two surfaces, one state machine.** `QuestionnaireSession` (on `GazeCondition`) owns the run of 24 screens — 1 framing, 2 previews, 15 rating, 5 ranking-plus-comment, 1 closing — and renders it twice: `QuestionnaireDisplay`, a world-space canvas on the participant's own vertex with **no input at all**, and `QuestionnaireOperatorPanel`, an IMGUI panel Unity draws into the desktop window and not into the eye textures. The participant reads the item and **answers aloud**; the operator types what they say. `GazeControl → Set Up Questionnaire` builds and wires all of it.

**Built 2026-08-27, after a VR verification where nothing appeared after a clip.** Only the data layer existed — the instrument, the screen list and the response writer, all pure and tested — and steps 2-4 of `questionnaire-ui-design.md` §9 had never been built, so a session paused with the agents hidden and showed nobody anything. Two decisions from that day also contradicted each other in the repo (the decisions log had the items in VR, `ClipPauseController`'s own doc had them outside it); the user restored the in-VR canvas, and it is what is built.

**Nothing is pointed at, on purpose** (§0). No XR Interaction Toolkit, no ray interactor, no controller path under the Varjo loader — which is the one hardware surprise this project has already had once. A rating screen is headed by the instrument's `ratingTitle` and lists the four items numbered, each behind a box — `>` marks the one being asked and the number the operator types appears in that item's box, so a participant can watch a spoken answer land and say so when it was heard wrong (2026-09-02, replacing the marker-only list that deliberately showed nothing back). **The ranking and the free-text probe share one page**, headed by `shortAnswerTitle` and numbered on from the rating items (5 and 6, derived from `perClipItems.Length`) (2026-09-02). It shows the two prompts and nothing else; D1 carries its own "(optional)" in the prompt and has no instruction line on either surface, while the ranking's "no ties" stays operator-side — under a foot naming the group about to be watched (`nextGroupFormat`, "Next: group 3"), which is the participant's only sense of where they are in a session of five and says nothing after the last group. **Both question pages are shown once before the first clip**, as the rating preview then the short-answer preview (`QuestionnaireScreenKind.RatingPreview`/`ShortAnswerPreview`, the matching `Phase`s), each answering nothing and passed with one press of the operator's key: a participant who knows they will rate four things and then rank the three versions watches the first group for what they will be asked about. The rating preview is the rating page itself with no entry behind it, so every box is blank and nothing carries the `>`. The operator still enters them as two screens, because they are two records and the ranking refuses a tie. **The ranking marks nothing at all** — it shows the prompt and no version list, because the participant names the three in order aloud and listing them only invited them to do the ranks-to-versions conversion themselves (2026-08-31). The rating screen's scale line is led by `scale.rangeHint`, composed with the scale's own bounds: the three anchors alone read as a three-option menu and participants asked whether they were choosing from 1, 4 and 7. **Nothing tells the participant to answer aloud any more** — `spokenAnswerInstruction` was on the foot of every page and is deleted from the instrument (2026-09-02); the operator says it.

**The operator panel is blinded** (§2). It shows `Conversation 3 · Version 2 of 3` and never the method behind a version. The experimenter reads the items aloud and knows the hypothesis, so naming the condition would tell them which answer is the interesting one; the condition reaches `responses.csv` straight from `StudySequence` and is displayed nowhere. Keys: `1-7` answers each item in turn, `Backspace` undoes, `Enter` commits the screen and releases the next clip; the ranking takes `1-3` with **ties refused**; the comment is a text field committed with `Ctrl+Enter`. Every key is read from `Event.current` inside `OnGUI` rather than through the Input System, so typing a comment cannot also enter a rating.

**A screen holds the session.** `ClipPauseController.AdvanceHeld` and `StudySessionRunner.StartHeld` are set while a screen is unanswered, and the pause controller yields the whole key — the skip included — so one operator key cannot walk past an unanswered screen. With no questionnaire in the scene both stay false and the pause works exactly as before. `GazeConditionRunner.StudySessionProblem()` refuses a study session with no `QuestionnaireSession` in the scene, because fifteen clips that ask nothing is a session that looks complete and measures nothing.

**Answers are written as they are entered**, into `<recordings root>/<participant>/`: `responses.csv` (`participant, block, conversation, version_position, condition, item, response, utc`) and `comments.jsonl` for the free text, which is kept out of the numeric file because it contains commas and newlines by nature. A screen is committed as a whole rather than per keystroke, so a mistyped answer can still be corrected — `QuestionnaireResponseWriter` takes each question exactly once and offers no amendment. A real participant's folder is opened once and never reopened; **`P00` takes a timestamped folder instead**, or the second development run of the day would refuse to start for a reason that has nothing to do with the study.

The entry rules are `QuestionnaireEntry` (pure, 17 tests): slots, a cursor, the scale bounds, and whether repeats are allowed. A clip that was **cut short** (`ClipPauseController.WasCutShort`) puts its screen up with recording disabled — a rating of half a clip is worse than a missing one, because nothing downstream can tell them apart.

It runs **only when `StudySessionRunner` is enabled**: a bake, a demo recording and a preview all press Play in this same scene, and turning that runner off is already how each of them says it is not a participant run.

Still to check on hardware: that the IMGUI panel really is invisible in the Varjo (§1 — the assumption the two-surface split rests on), and legibility at 1.5 m. Panel geometry lives on `QuestionnaireDisplay` (`EyeHeight`, `Distance`, `PanelSize`, `BodyFontSize`), which places itself in `Awake` rather than trusting the scene transform — a `RectTransform`'s position is expressed through anchors and an offset written by a setup script does not reliably survive.

## Agent appearance

**Match the textures to the segment's voices — per clip, at load.** The corpus records nothing about who is speaking, so `Tools/find_demo_segments.py` measures it: median F0 over each speaker's own voiced frames, written into `segment.json` as `voicePitchHz`/`voice`, and filterable with `--voice male|female|mixed`. `AgentAppearance.MatchToVoices` applies that measurement, called from `RecordedConversation.TryLoadSegment` so that *every* path which loads a segment gets it: the study session, the clip browser's **Load and Play**, a plain Play and a bake.

**Nothing did this at runtime until 2026-08-27**, and a session therefore ran all fifteen takes on whichever textures the scene was last left on — two women speaking a male-male recording, on every frame a participant then rates. The scene's committed materials are only where a clip starts from; the clip decides. The five study clips are male-male, female-male, male-female, female-female and female-male, so at least three of the five were wrong however the scene was left.

Who gets which is `AgentSkins` (pure, unit-tested): **the stock albedo goes to the lowest speaker code of each measured voice**. There is exactly one stock albedo per sex, so a mixed pair puts both agents on stock and a same-sex pair leaves speaker 2 on a SMPLitex texture with the face misregistration below. The four materials — `SMPLX-Female-URP-AgentA` (stock `smplx_texture_f_alb.png`), `SMPLX-Female-URP-AgentB` (`smplitex_f00021_alb.png`), `SMPLX-Male-URP` (stock `smplx_texture_m_alb.png`) and `SMPLX-Male-URP-AgentB` (`smplitex_agentB_alb.png`), all on the stock normal map of their sex — are loaded from `Assets/SMPLX/Materials` by path in the editor, for the same reason the segment's audio clips are (a build would need them wired in the scene). A `voice` of `unclear` decides nothing and leaves that agent as it is, with a warning. **GazeControl → Clip Browser**'s *Match textures to voices* runs the same code as a persistent scene edit, for previewing in Edit Mode.

A SMPLitex output needs two passes before it is usable, both editor menu items under **GazeControl → Textures**:

1. **Composite SMPLitex Eye Disc** — SMPLitex never generates the eyeball UV island and leaves it black, and both eyes share that one island, so an untreated texture gives an agent black eyes. The disc is copied from a stock SMPL-X albedo; it sits at (296, 221) r≈19 in 512²-scale, **top-left origin**.
2. **Pad SMPLitex UV Islands** — fills the gaps between islands from the island edges, using the mesh's own UVs as the coverage mask so nothing a triangle covers is ever written. It also repairs the generator spilling a flat background colour *into* an island, but only when the background is measurably flat (the mode holds ≥50% of outside texels); every female SMPLitex texture tried fails that test and is padded only.

Only the *body* is female. `SMPLX.modelType` stays `Male` on purpose: it selects the betas-to-joints regressor and so moves the **skeleton**, not the mesh surface, and the FBX carries one template mesh. A genuinely female body would need a female template export or non-zero betas.

**Known artifact: SMPLitex textures do not register with the mesh's UVs on the face.** The nostril shading lands below the actual nostrils, on the upper lip and nasolabial fold, and the same offset is visible on every SMPLitex sample tried (`f00016`, `f00017`, `f00021`). The **mesh is not at fault** — this was tested on 2026-08-16 by putting the stock Meshcapade albedo on agent A: its nostrils land exactly right on the same mesh, same material, same normal map, while agent B's SMPLitex texture beside it stays displaced. So the misregistration is in what SMPLitex generates, not in the FBX's UVs or the Blender mouth-bag re-export. Nothing here corrects it: a fix would have to warp the generated face island onto the SMPL-X template, which is a real piece of work and has not been attempted.

Because of that, **the stock albedo is spent on agent A** (from 2026-08-16, and it is why `AgentSkins` hands stock to the lowest speaker code): stock needs neither of the two passes above — it is the eye-disc donor and its islands are properly laid out — so on a same-sex clip the offset lands on agent B rather than on both. There is only one stock albedo per sex, so B cannot take the same fix without the two agents becoming the same person. On a mixed clip nobody is on SMPLitex and the offset is absent from the take entirely.

Agent A's earlier sample `smplitex_f00016_alb.png` was deleted on the same day (it fit the body badly and carried yellow-green painted onto the fingers and toes *inside* the UV islands, an artifact of the sample that no colour statistic could separate from legitimate content). It lives only in git history.

## Motion data conventions

TalkingWithHands clips come in pairs from the same recorded take: one `interloctr` file and one `main-agent` file whose names differ only in that token. **The two agents must always play a matched pair**: one agent uses the `interloctr` clip and the other the `main-agent` clip of the same take. Mixing takes would put two unrelated conversations in one room, and the corpus is *Centered* — each file's `trans` and global orientation are expressed in a frame anchored on that file's main agent, so only the two sides of one stem are mutually consistent.

`SmplxMotionPlayer` plays a clip whole or as a segment (`StartFrame`/`FrameCount`), and root translation is anchored on the segment's **first frame**, not the clip's — several minutes into a recording the root has wandered far from where it started. Clear `Autoplay` when an external timeline calls `Seek`, which is what `RecordedConversation` does. A player whose `ClipPath` is empty **does not load on `Start`** — its clip is assigned by whatever owns it (the three-party replay does that at load), and loading an empty path opened the project folder as an archive and reported an access error that named nothing relevant.

**Clearing `RootTranslationRelative` places the pelvis at `template_J[0] + trans`, in the player's own frame** — SMPL-X's own convention, and the rig's bind pose *is* `template_J[0]`. It used to write `trans` as a local position, which is wrong twice over: it drops the template offset, and the pelvis's parent in the FBX (`root`) sits **1.36 m** up so the rest body stands on the floor, so every body floated by that much. Nothing had noticed, because the study path only ever uses relative mode, where the constant cancels. Fixed and tested 2026-09-08; a grounded 3People clip now puts its toe joints at 0.02 m, which is what the converter grounded them to.

Only two example clips are committed (via LFS); other `.npz` files under `Assets/MotionData/` are git-ignored, and the demo reads its motion straight from the corpus.

Three things that will otherwise cost a session:

- **`Separate/..._PC_<N>_...` is mislabelled.** The `N` is an alphabetical position, not a participant number, and it is wrong in 16 of 21 slots. Gaze, audio and `raw_data/` carry true PC numbers; the processed motion does not. Join on the subject name via `mocap/<date>/Notes.xlsx`, which is the participant register **and** the per-stream sync sheet.
- **The two reference readers in `{TPC_VIEWER}` use different Euler orders** (`Data/main.cpp` XYZ, `Demo/main.cpp` XZY). **It is XYZ, measured**: fitting the C3D markers to the posed source skeleton leaves 2-6 mm under XYZ and 40-300 mm under every other order (`--check-markers`). Still behind one named constant. Marker-based fitting from `{TPC_VICON}` remains the higher-fidelity route; **angle retargeting is the chosen first route** (user, 2026-09-07) and is built.
- **The source has 19 joints against SMPL-X's 55** — no neck, no spine subdivision, no fingers. Jaw and eyes must stay zero in the clip: LipSync and `IGazePolicy` drive them at runtime.

**The converter is `Tools/convert_3people_smplx.py`** (2026-09-07): all 69 participant-sessions are at `F:\Data\3People-2022-SMPLX\<date>\Session_<S>_pc<N>_<Name>.npz`, room frame horizontally, grounded vertically, default body. Its docstring is the design record. It reads the stacked CSV (never the `Separate/` txt — the CSV block order is not always alphabetical) and resolves the participant through `Notes.xlsx`. The C3D markers have gaps stored as zero points; the published `gazeBehavior.txt` cannot be reproduced from the files on disk and is not relied on.

**Segments come from `Tools/find_3people_segments.py`** (2026-09-08): 10-30 s windows with at least one end-of-turn event in which one participant never takes a turn — two takers (A/B, lowest PC is A) and a listener (L). The events are `{TPC_EOT}` = `F:\Data\GazePattern\EoT_2022`, built by `{GAZETURN}` = `F:\Code\scnpro\prototype\prototype\gazeturn` (`gazeturn/labeling/eot_events_2022.py`) from `Caption/*_sentence.csv`; the doc's "End-of-turn events" section has the schema and provenance. Speaker codes are true PC numbers. Event times, caption times, the trimmed wavs under `{TPC_DATA}/audio_text` and the converted npz all share one clock from the same instant, verified on all 23 sessions. The captions are automatic and carry `[Music]` rows and microphone bleed; a tag-only row rejects a window, bleed can only be caught by reading `--inspect`. Motion glitches are reported per window, not filtered (user's call): the legs are dealt with later. **Which participant becomes what is undecided** — the user wants to watch full original clips with all three first. Nothing is exported yet.

**Sessions are watched in their own scene** (2026-09-08): `GazeControl → 3People → Set Up Replay Scene` builds `Assets/Scenes/ThreePartyReplay.unity`, and `ThreePartyReplay` plays all three participants of one session at once off a single clock — the same one-DSP-instant scheduling `RecordedConversation` uses, because three microphone tracks of one room drifting a frame apart is audible on every overlap. Not `TriadScene`: the study's starting viewpoint is a controlled variable, and this camera orbits, since the three face each other and a fixed camera always has someone's back to it. **The room places the bodies, not the scene** — the motion players run with `RootTranslationRelative` off, so the three seats' transforms must stay identity or the participant leaves the room they were recorded in. Audio is read straight off disk as just the requested window (`WavSegment`, pure and unit-tested; a whole ten-minute stereo session decodes to 230 MB per participant, so Unity's own loaders are not usable). `ThreePartyOverlay` names each body, shows its live caption and marks the annotated events. No gaze policy runs, the eyes stay where the mocap left them, and nothing is logged: this is for deciding who becomes what, not for measuring.

**`GazeControl → 3People → Session Browser`** picks the date, session and window, lists the finder's ranking from `output/3people_segments.csv` as a starting point, and **reads a window out as a transcript with its events marked before anything plays** — the editor-side counterpart of `--inspect`, and the only way to catch the microphone bleed that puts a phantom line, and so a phantom event, on the wrong track. Play whole session ignores the ranking, which is what watching the originals means.

**The participant replaces the listener** (user, 2026-09-08). Of the three recorded people, the one who never takes a turn — no end-of-turn event names them; at most a backchannel — becomes the study participant's seat, and the other two become the agents. `ThreePartyReplay` derives that participant from the events inside the window (`ListenerPc` overrides it), and `ThreePartyViewpoint` (pure, unit-tested) measures the seat from the recording rather than authoring it: **position is the mean eye position over the whole window**, not the pose at any one frame, and **the opening facing is the direction to the midpoint of the two speakers' eyes at the first frame**, so the clip opens with both of them in view whatever the room layout was.

**It is the converted body's head, not the recorded person's, and everybody keeps the default body** (user, 2026-09-08). The converter poses a **default SMPL-X male with betas all zero** (all 69 clips, the women included) at the participant's real room position, so horizontally the seat is theirs and vertically it is the template's — nothing in the motion layer reads `betas` at all. `ground_offset_m` in each npz is exactly that discrepancy at the pelvis, and it runs from **−1 cm to +17 cm** across these participants: Clayton and Benjamin are the default body's height, Karthik 3 cm shorter, Crystal 10 cm, Joseph 9 cm, May 17 cm. Crystal's own eyes were around **1.54 m**; the seat measures **1.71 m**.

**Recovering the real heights is not needed, because the gaze is derived by target and not by absolute angle** (the user's reason, and it is the one that settles it). Every gaze decision in the system names a target: the prototypes are role-coded, `GazeController` aims at the target's `LookAtAnchor` in whatever geometry is rendered, and the participant's own gaze resolves through a 0.15 m head sphere. The flattened heights (≈7-9° of elevation at a metre) change the rendered angle, not which target anything names, and stay well inside `GazeController`'s ±25° pitch clamp. It is also identical for every participant, so it is a constant of the apparatus rather than a confound — and seating the participant at their real height under default-bodied speakers would have *opened* a gap the recording did not have. Per-participant shape (the VSK anthropometrics, or the deferred marker fit) remains available and would correct the seat for free, since `ThreePartyViewpoint` measures the posed skeleton rather than storing a constant. Yaw only, as in `ViewRecentring` — pitch and roll come from the headset against gravity and are already right. Eyes rather than the head bone, the same two joints `ParticipantEyeHeight` measures. **V** in the replay stands in that seat with the listener's body hidden; dragging turns the head and moves it nowhere (the study rig itself tracks translation too since 2026-09-08).

**Seven clips are chosen** (user, 2026-09-08) — see `Assets/Docs/3people-motion-sources.md`; **the session runs five of them**, `study2_c5` and `study2_c6` dropped the same day (user), so a session is 15 takes and Fig7e and Fig8e are never played. All are 10.9-18.6 s with exactly one annotated event, six a turn-taking and one an interruption, and in five of the seven the listener says nothing at all.

**The study is being redesigned as the triadic prototypes played in a triad, with the participant's gaze as an outcome measure** (user, 2026-09-08). `Assets/Docs/study2-design.md` is the design and the handoff; read it before touching this work. In one line: the participant stands in the listener's seat, the agents play the prototypes' speaker columns **baked and open-loop exactly as in study 1**, and the participant's tracked gaze is measured against the listener column rather than used to choose anything. A gaze-driven *retrieval* of the prototype was settled on first and withdrawn the same day: only four of the fifteen prototypes ever aim an agent at the listener (60 of 900 agent-frames), so the selection would have been invisible to the participant while costing `GazeTrackBaker`'s reproducibility — §2 of the doc has the table. Contingent completion (branch on returned gaze) is the deferred study 3. This supersedes the three-condition, fifteen-clip design under "Running a session" above.

**Study 2 replaces study 1's corpus and nothing else** (user, 2026-09-08), and that is how it is built:

## Working in this repo

- **Python scripts run from the repo's uv environment**: `pyproject.toml` at the root, `uv sync` once per clone (creates the git-ignored `.venv/`), then `uv run python Tools/<script>.py`. The interpreter on PATH has no numpy. `identify_speakers.py` needs the opt-in `speaker` group (`uv sync --group speaker`, torch + speechbrain).
- This is a Unity project: every asset file has a paired `.meta` file. When adding, moving, or deleting assets outside the Unity Editor, keep `.meta` files consistent (let the Editor generate them where possible, and always commit them together with their asset).
- Scenes, prefabs, and most `.asset` files are Unity YAML (see `.gitattributes`); binary media (models, textures, audio) go through **Git LFS**.
- Tests use the Unity Test Framework and run inside the Unity Editor (Test Runner window, or via the JetBrains Unity test tooling when available).
- **`Research/` holds local-only material** — raw gaze corpora (`corpora/`), reference PDFs (`papers/`), working notes (`notes/`). Everything there is git-ignored except its `README.md`. It sits outside `Assets/` deliberately: Unity imports every file under `Assets/` regardless of `.gitignore`, generating `.meta` files and Library entries for data that is never a runtime asset. Put reference material there, not under `Assets/Docs/`. **The paper is no longer among it** — see `{PAPER_ROOT}` above.
